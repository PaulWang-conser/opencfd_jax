# 第 1 步前：补齐回归检查与基准来源记录

## 目标和范围

在开始单块 `MeshData` 改造前，修正 Step 0 检查器可能误报 PASS 的情况，并为现有基准补充可追溯的源码和输入记录。此任务不改变求解器数值，不进入第 1 步，也不覆盖现有 `baseline/`。

目前基准是 2026-11-17 12:52:43 生成的 7 个 WENO7 + CD8、FP64 CPU 用例；清单记录提交 `8bdc59776f02` 和 8 个脏文件，但未记录当时的差异。`experiment/README.md` 还记录了 WENO7 epsilon 修正后的原码单步对拍。请保留这些数据及记录。

## 任务 1：检查器拒绝缺失和异常

修改 `check_step0.py`，并添加有意义的回归测试：

1. 每个 NPZ 的字段集合必须完全一致；缺字段、多字段、缺 `_meta`、元数据无法解析都报 FAIL，明确列出文件和字段。按现有口径严格比较 `t`、`step`、`dt`，缺少其中任何一项也报 FAIL。
2. 保留并检查数组形状和 dtype，避免当前先统一转换为 float64 而掩盖 dtype 变化。数值字段出现 NaN、正无穷或负无穷时默认 FAIL，报告位置和类型；现有基准记录显示各场均有限，因此不必为非有限值一致设置宽松例外。
3. 明确区分精确比较与容差比较。若继续称 `--tol 0` 为逐位一致，就必须比较原始 dtype 的表示，包括正负零；否则明确改称数值完全相等。保留现有容差模式、报告结构和返回码的兼容性，任何调整在 README 说明。
4. 校验基准文件存在且其 SHA-256 与基准清单一致，防止基准内容被改后仍被拿来比较；读取损坏文件、空文件集合等应报错而非 PASS。不要在检查时修改基准文件。

测试至少覆盖：字段缺失和多出、缺失或损坏 `_meta`、缺少 `t/step/dt`、形状或 dtype 不同、NaN/正无穷/负无穷、基准哈希不匹配、正常精确相等与容差内外差异；测试要验证命令的退出码及报告。若选择逐位语义，再测试正负零。测试先证明旧检查器不能识别问题，再修复并验证。

## 任务 2：记录当前状态并核查与既有基准的关系

1. 不要声称现在的源码就是基准生成时的源码：当时只记录了脏文件数量，无法仅凭提交号还原。保留原 manifest 和基准产物，另存一份来源记录，明确标注“事后采集”，附采集时间。
2. 在来源记录中保存当前提交号、分支、`git status`、已跟踪文件的 staged 和 unstaged 差异，以及本次基准实际使用的源码、配置和输入文件的路径与 SHA-256；对未跟踪但运行需要的文件也记录内容或可恢复副本。记录运行环境、命令和外部输入（包括 quick 网格与初场）的实际位置及哈希。避免纳入输出、缓存、大型无关数据或敏感内容；不要改变用户已有改动的暂存状态。
3. 在与基准相同的环境下，将**当前源码**的 7 个用例跑到独立候选目录，用修好的检查器和原基准比对。报告每个用例结果和实际环境；不要用 `--phase baseline` 重写原基准。即使全部一致，也只能说明这 7 个输入与输出相符，不能证明当前源码与当时逐字相同。
4. 若存在差异、缺失基准输入或无法取得原环境，保留现场、报告准确原因及影响；不要修改阈值或重建基准来掩盖。若将来要更新基准，另建版本并说明原因及新旧关系。
